# The term project: one question about the G1, answered by measurement

Weeks 12-15 and the final-exam slot. Teams of two or three choose one question about the
simulated Unitree G1, build the experiment that answers it, and present the answer with
the robot running in the viewer.

**What a project is.** A project is a question asked of the robot plus a measurement that
answers it. It is not "make the robot do something cool", and it is not "train until it
works". "Can MPPI recover from a 300 N shove *and stop within 0.5 m*?" is a project.
"Make the G1 dance" is not, until it says what will be measured and what would count as
failure.

**Simulation only.** There is no hardware, and no project may need any. Everything runs
on the laptop you used in the labs, with the environment `uv sync` gives you
(`uv sync --extra rl` for anything that learns). A project may use only the course
package `soc4180`, its week scripts, and what `uv.lock` installs.

## 1. What you hand in

| part | what it is | where it lives |
| --- | --- | --- |
| **the question** | one question about the G1, with the quantity that answers it | proposal, report |
| **the prediction** | written **before** the first real run: a number and the reason for it | proposal (dated), report |
| **the twin** | the same run with **one** thing changed, so a difference has a cause | your script |
| **the measurement** | one script that runs the experiment and writes every number to `results.csv` | your team folder |
| **the check** | a one-line rule decided before the final run, printed as `CHECK PASS` or `CHECK FAIL` | your script's last line |
| **the demo** | the run that matters, replayed or live in the MuJoCo viewer | the presentation |

Put everything in **`weeks/projects/teams/<team-name>/`**: `project.py` (copied from the
template), `results.csv`, `proposal.md`, `report.md` and any trained checkpoint. The
checkpoint must be small enough to commit, or must be regenerated by `project.py` in
minutes.

## 3. The method (the part that is graded hardest)

Every lab since week 7 has run this way. A project follows the same five rules, and the
[template](templates/project_template.py) builds them in:

1. **Predict first.** Write the prediction, with a number, before the first real run, and
   date it in the proposal. A wrong prediction is expected and costs nothing. A
   prediction written after the result is worth nothing.
2. **Run a twin.** Compare against the same run with exactly one thing changed: the
   controller, one weight, one sensor, one randomisation. If two things change, you can
   no longer say which one caused the difference.
3. **Every number comes from `results.csv`.** If a number is in the report or on a
   slide, the script wrote it. A run you did not save did not happen.
4. **Decide the check before the final run.** For example: "yours survives at least
   10 N more than the twin, in every seed." Report a `FAIL` as a `FAIL`, with your best
   explanation. A clear negative result with a diagnosis is a good project (week 8's PPO
   run got *worse*, and finding out why was the lesson).
5. **Judge by margins, never by a float from a fall.** A falling robot is chaotic: a
   1e-12 rad nudge changes where it lands, and different machines give different
   numbers. Compare which force first knocks it over, how many of N runs fail, or
   whether it stays above 0.5 m. Never compare the third decimal of a fall.

**Never grade convergence; grade the diagnosis.** If your learning run does not
converge, measure *why*: survival under exploration noise, the reward split by term, the
exploration std. That is a result.

## 4. Starting points

[`catalogue.md`](catalogue.md) lists thirteen projects. Each comes with the script to
start from, a baseline already measured in the course, a twin to compare against, and
the trap we already know about. They cover the whole course:

| area | projects | lectures |
| --- | --- | --- |
| analytic walking and actuation | P1 walk farther, P2 the walker on hard ground | 4, 5 |
| sensing and balance | P3 balance from the robot's own senses, P4 reach while standing | 2-3, 6, 7 |
| learning to act | P9 reward design for stepping, P13 a table that balances | 7b, 8 |
| robustness | P8 learned push recovery | 9 |
| planning and imitation | P5 push recovery by planning, P6 new tasks for the planner, P7 a planner with a wrong model, P10 distil the expert | 10 |
| perception and language | P11 eyes on the ball, P12 words to actions | 11 |
| anything else | P14 your own proposal (approved in week 12) | - |

**Mind the compute.** A laptop runs a few hours of simulation per evening. Week 9's push
policies took about 16 minutes each on a 36-core machine and will take hours on a
laptop. Use the shipped checkpoints, retrain small, or ask for the Colab GPU route
(week 9) early. MPPI decides at about 0.35x real time on 16 threads, so a 10 s planned
run takes about half a minute or more.

## 5. Rules

- One question per team. Two teams may take the same catalogue entry if their
  questions differ.
- Simulation only, the lock file only. Ask before adding a dependency. If it is
  approved, it goes into `uv.lock` for everyone.
- Your code is yours to change. Code copied from the course is fine; say where it came
  from in the report. Code from elsewhere must be cited and its licence stated.
- AI assistants may help you write code and text. You must be able to explain every
  line in the presentation, and every number must still come from your own
  `results.csv`.
- **Never claim the robot falls with `ctrl = 0`.** Its servos hold zero (week 0). To
  show an uncontrolled robot, use `soc4180.actuation_disabled`.

## 6. Grading (suggested weights; the instructor sets the final ones)

| part | weight | what earns it |
| --- | --- | --- |
| proposal | 10 % | a measurable question, a dated prediction with a reason, a named twin |
| check-ins 1-2 | 15 % | the script runs headless in class; the rule is committed before the final runs |
| method | 30 % | twin, seeds, margins, every number traceable to `results.csv`, the check decided in advance |
| result and honesty | 25 % | the answer stated plainly, including a `FAIL`; the explanation is tested, not guessed |
| presentation and demo | 20 % | the robot runs in the viewer; the table and the check line shown; questions answered |

Ambition counts only through the method. A small question answered cleanly scores higher
than a large one answered vaguely.
